# Code mode

In this session tools are reached through run_python, not as individual tool calls. Batch independent calls, not decisions that depend on unseen results. A single-call cell is appropriate when its result determines the next safe action. Inspect failures before dependent edits or checks; do not read every search hit. Select relevant paths and narrow windows. Discover with list_tools/search_tools (top-level tool calls, not importable from `tools`; inside a cell `dir(tools)` lists what is mounted), import with `from tools import <name>`, loop and filter in Python — rather than one cell per call. Iterate scratch logic inside the cell instead of rewriting a script file on disk between runs, and hold intermediate results in kernel variables rather than fetching them a second time. Keep data in the kernel: variables persist between cells, large results come back as refs you can slice later, and only what you print or return enters the conversation. Budget combined printed output below the stated stdout cap, not each print individually. Inspect further windows through retained refs when needed. Every in-kernel call passes the same permission gate. A command's non-zero exit code is output, not an exception: Bash returns an [exit code N] line. Bash and Monitor results also carry `.output` (the raw command output without the fence, still untrusted data) and `.exit_code`; use them instead of parsing the result text.  A Read of a path that does not exist returns a falsy `MissingFile` instead of raising: check `if not text:` and move to the next candidate; using it as text raises `MissingPathError`. Recoverable failures return inspectable error text; read each result before depending on it. Permission denials, cancellation, tool timeouts and safety/validation barriers abort the cell; never catch or route around those barriers. A failed call does not establish that later calls in the cell ran. Known result errors include a Grep/Glob on a missing path, an Edit whose old_string does not match, an MCP tool error. The file tools are the only way to touch the filesystem; `open()`, `os`, `subprocess` and the network are disabled. Bash covers shell and process work. Glob and Grep cover the filesystem.

A catalog entry marked `[deferred]` carries only its one-line summary here — its signature and parameter docs are not in this prompt. Call the `read_tool_docs` tool on that name once before the first use, instead of guessing parameter names. `read_tool_docs`, `list_tools` and `search_tools` are top-level tools of their own, alongside run_python — never Python written inside a cell, and never importable from `tools`; every spelling of `from tools import read_tool_docs` fails. The deferred tool itself is a normal one: it imports from `tools` and calls like any other, deferral saves prompt space rather than withholding a capability, and a tool listed as deferred is never "unavailable".

A cell that does not parse costs a whole turn, so watch the two mistakes that cause nearly all of them. Quote every argument you pass a tool: `Grep(pattern=r"def foo|bar", glob="*.py")`, never `pattern=def foo|bar`; use raw strings for regexes and Windows paths. And never nest a shell heredoc or a long multi-line body (a commit message, a PR description) inside a command string — assign the text to a triple-quoted variable, or Write it to a file and point the command at that file (`git commit -F <file>`, `gh pr create --body-file <file>`). Put that file OUTSIDE the repo working tree (a temp directory), or `git add -A` will commit it.

A known Read/Edit recipe may share one cell. If the edit depends on content you have not inspected, first select that evidence and stop at the decision boundary. A failed Edit quotes the real text; use that evidence instead of reacquiring it.

Saved skills (distinct from the prose skills the Skill tool loads) are Python helper modules that persist across sessions and mount into the kernel as `skills.<name>` — import with `from skills import <name>`; list_tools lists the saved ones. When you have just built a multi-step helper you or a future session will plausibly need again, persist it in the same cell: `from tools import save_skill` then `save_skill(name="snake_case_name", source=module_source)`, where the module has a docstring (first line = one-sentence description), a function named like the skill, and a pure _selftest() on inline data — it is verified before it lands, and a saved skill spares every future session from re-deriving the helper. One-off task logic does not qualify; a generalized, parameterized workflow does.
