# Performance sprint 2026-10: baseline

This is the "measure first" step of the sprint (method:
`perf-sprint` skill, sections 2 to 4). It records a repeatable baseline for
the owner's three journeys, the critical path of each, and a ranked list of
candidate projects with estimates and the deterministic count that would
guard each one. Nothing in the app changed for this baseline.

- **Revision measured:** worker `0.9.1-dev.92+g04d9a0cfb` (the live worker on
  2026-10-07, read with DeployStatus before each pass).
- **Kind of number:** lab, but on field data: headless Chromium 154
  (`/usr/bin/chromium`) driven by `scripts/perf/journeys.mjs` against the live
  worker's preview listener, so the owner's real sessions, projects and
  worktrees are what loads. There is no field telemetry yet; PR #1989 adds the
  `shuffle:app.bootstrap:*` / `shuffle:chat.open:*` measures and the
  `perf.agent_startup` log stages, and none of them are on this revision.
- **Machine:** ServerWorker worker, AMD Ryzen 9 5900XT (32 threads), browser and
  worker on the same host, no network or CPU throttle. Host load average 1.0
  to 2.5 during the passes.
- **Statistic:** nearest-rank p75 of 20 runs per cell, after one discarded
  warm-up run, with min and max. Milestones are sampled on
  `requestAnimationFrame`, so they resolve to one frame (16.7 ms).
- **Repeatability:** the desktop matrix ran twice, 30 minutes apart. Every
  p75 agrees within 8% (the large cold open moved 7.7%, everything else 0 to
  7%); raw values are in the appendix.

### Agent SessionSearch: mirrored-event trigram index (Refs #2000)

**Measured path, not the UI global search:** the native harness binds
`ctx.extra["session_search"] = store.search`; the delegated builtin bridge
also binds `PgFluidStore.search`. Both reach `fluid_pg_store._search_sync`.
This lab times that synchronous DB backend through scoring, permission
filtering and title/project decoration. It does not time a model turn, tool
formatting, worker-to-worker network traffic, or the browser. No live session,
owner database, paid model call or production configuration was used.

At baseline `4b00e4b0d` the native and delegated stores **already had**
`pg_trgm` GIN indexes. The mirrored `session_events` arm added by #1999 did
not. The change adds `idx_session_events_recall_trgm` on `(payload::text)`
only for `message.user`, `message.assistant`, and `assistant.text_delta`.
It leaves every query, SQL prefilter score, Python substring check, ranking,
row/session cap, cross-worker fold, project scope, and access check unchanged.
A token/English FTS substitution was rejected because it would lose substring,
short, punctuation and non-English recall.

#### Fixture and protocol

ServerWorker, AMD Ryzen 9 5900XT, PostgreSQL 16, UTF-8 / C locale, default planner
settings, loopback only; synthetic data in a newly initialized, session-owned
cluster. Explicit `ALLOW_REAL_PG=1` and a disposable loopback
`TEST_POSTGRES_DSN` were required. The app's actual `init_database()` built
both the baseline schema and the upgrade index; no hand-created substitute
index was used. All long commands ran through Monitor.

- 1,300 sessions: 450 native, 450 delegated, 400 remote-owned mirrors.
- 32 messages per session: 14,400 native nodes, 14,400 delegated entries,
  12,800 mirrored user events (41,600 searchable JSON rows).
- Each text consists of 80 space-separated chunks of
  `log code sample ` plus `md5(i || '-' || j || '-' || k)`, with session `i`,
  message `j` and chunk `k`; approximately 3.8 KB per message. This gives
  mixed searchable prose and incompressible code/log identifiers, not empty
  rows or repeated highly compressible filler.
- Sessions divisible by 13 have `zebrafish quokka capybara 東京 50%_complete a.b xy x`
  appended to their first three messages. Thus all arms contain selective
  three-term matches; `log code sample` matches every message. Native blocks
  use the producer's `kind: text` shape, delegated entries use
  `type: user / message.content`, mirrors use `message.user / content`.
- Unique timestamps (`i * 100 + j`) and fixed synthetic titles; native
  project root `/lab`. No fixture rows were changed between the measured
  baseline and upgrade. `ANALYZE` preceded both passes.
- One discarded warm-up followed by 20 runs per three-term query;
  nearest-rank p75 (15th sorted sample), `perf_counter` elapsed time. The
  baseline was measured **before implementation edits**, and the upgrade
  used the same database. Database size was 561 MiB before, 609 MiB after
  (including existing-index bloat from fixture preparation).

| query | baseline p75 (min–max), ms | indexed p75 (min–max), ms | result |
|---|---|---|---|
| `zebrafish quokka capybara` | 1464.02 (1430.18–1493.50) | 64.35 (63.02–72.21) | 22.75x; below 1 s |
| `log code sample` | 2826.38 (2719.19–2917.51) | 2867.41 (2728.07–2996.49) | no material improvement; above 1 s |

Additional **two-run smoke checks, not reliable percentile measurements**:
unknown term 453–454 to 0.78–0.80 ms; `50%_complete` 594–598 to 52 ms;
`東京`, `xy` and `a.b` approximately unchanged at 0.77–0.85 s; `x` still
1.36–1.37 s after indexing. Terms with no usable trigrams and queries matching
most rows can still scan/recheck large amounts of text. The broad query's
existing native/delegated scoring and mirrored-message folding dominate;
an index alone cannot make that work disappear without changing semantics.
**This is a partial resolution: Refs #2000, not Fixes.** No claim is made
about the owner's reported 4–8 s workload or all-query sub-second recall.

Full ranked `SessionSearchHit` objects (IDs, score, best, recency, texts,

were compared locally, not printed or exported.

`tests/db/test_agent_session_search_postgres.py` is an opt-in real-PG
regression. It exercises the bootstrap and actual fingerprint-gated startup
upgrade, idempotency, and captures all three real agent prefilter SQL queries
for a normal-planner index-path assertion. Its smaller deterministic corpus
uses inline synthetic code/log text to make heap scan cost visible to the
planner, and flushes bulk insert GIN pending lists before `ANALYZE`. It also
compares exact indexed/forced-scan ranked hits for long, one/two-character,
Unicode, punctuation, `%` and `_` terms, with caller exclusion. Existing
recall/account tests continue covering API-key/member/owner visibility and
cross-worker behavior. Migration unit tests inject extension/index failures
and assert savepoint rollback, release and the degraded-search warning.

Run only against a disposable loopback test database, with the two guard
variables set, then:

```sh

```

#### Rollout cost and fallback

Bootstrap and upgrades share one idempotent DDL helper; changing the
migration source fingerprint ensures current-version installations receive
the index without a schema-version bump. Startup's existing advisory lock
serializes concurrent initializers. `CREATE INDEX` is intentionally inside
that transaction (not `CONCURRENTLY`): first upgrade has CPU/disk/WAL cost,
delays startup and can block concurrent writers until the build commits.
Build duration and write-throughput overhead were **not measured**. The
partial predicate avoids indexing tool/status events but includes local text
events too, because ownership is on the joined sessions table.

`pg_trgm` must be installed on the PostgreSQL host; creating the extension
requires database privileges (and index creation requires table authority).
App-managed PostgreSQL normally has those privileges; this lab used its own
cluster owner. A denied/unavailable extension or index rolls back to a
savepoint, logs a warning, and preserves correct unindexed recall instead of
aborting startup. It does not bypass permissions or install server packages.
After privileges/packages are corrected, a later migration-fingerprint change
or an explicitly authorized `FORCE_DB_MIGRATIONS=1` startup retries the build;
the successful overall startup fingerprint otherwise skips it. Neither was
applied to the owner's running worker here.

## How the rig works and how to run it

`scripts/perf/journeys.mjs` launches Chromium through `playwright-core` (the
repository already ships it as a dependency of `browser-mcp/`; nothing new is
installed), signs in once with an access URL, then for every run creates a
fresh browser context with that sign-in, so "cold" means an empty HTTP cache
and an empty in-page store while "warm" re-uses the page. Each run records:

- milestones sampled on every animation frame: composer present and
  enabled, first sidebar row, sidebar list complete (row count stable and
  equal to the cards the API returned), transcript rows rendered and
  settled, the Assistant home's "Open conversation" button;
- navigation and paint timings (FCP), long tasks over 50 ms with their start
  times, main-thread time from the DevTools Performance domain;
- every resource timing (path, start, duration, transfer bytes) and, for
  the event feed, a tap that records response headers, first byte and the
  `caught_up` event of the replay stream;
- for `send`: Enter keydown, the WebSocket `query` frame, the echoed user
  message, the first agent frame and first token in the DOM, and completion.

It prints a table per cell (p75, min, max) and writes all per-run data as
JSON, together with the revision, viewport, host load, N, warm-up count and
the data sizes it saw. `scripts/perf/stats.mjs` holds the nearest-rank
percentile code; `node --test scripts/perf/stats.test.mjs` tests it.

```sh
cd browser-mcp && npm ci && cd ..           # once, for playwright-core
export PERF_ACCESS_URL='<preview-access URL from your workspace facts>'
# journeys 1 and 2, desktop, 20 runs + 1 warm-up per cell
node scripts/perf/journeys.mjs --journeys launch,open --runs 20 \
  --viewport 1280x800 --small <small chat id> --large <large chat id> \
  --other <any third chat id> --out /tmp/perf-desktop.json
# same at mobile width
node scripts/perf/journeys.mjs --journeys launch,open --runs 20 \
  --viewport 390x844 --small ... --large ... --other ... --out /tmp/perf-mobile.json
# which API requests block a milestone: delay each path by 1.5 s in turn
node scripts/perf/journeys.mjs --probe open.large.cold --probeRuns 3 \
  --small ... --large ... --other ...
# journey 3 (sends real prompts: creates one chat, archive it afterwards)
node scripts/perf/journeys.mjs --journeys send --sends 1 --model '<cheapest model id>'
node scripts/perf/journeys.mjs --journeys send --sends 4 --sendSession <that chat id>
```

The access URL is a credential: keep it in the environment. The rig prints
only its origin and never writes cookies or storage state to disk. One
desktop pass of journeys 1 and 2 takes about 8 minutes; run it through a
background task, not a foreground shell.

Known limits of the rig: milestones are frame-sampled (16.7 ms
resolution); the browser and the worker share one host, so heavy server work
also steals client CPU; the probe mode's delay is applied in the browser, so
a probe can only show whether the client waits for a response, not why the
server is slow. Desktop pass 1 and 2 used an earlier version of the
Assistant-home check (rail button and "Open conversation" button both
present); the mobile pass and the committed rig use the visible
"Open conversation" button alone, which is the same moment on desktop.

## Journey 3: send a message

The rig sent 5 prompts in one throwaway chat (one first send that created
the chat, then 4 follow-ups) using the cheapest model available.

| send | Enter to user echo | Enter to WS `query` frame | Enter to first agent frame | Enter to first token | Enter to done |
|---|---|---|---|---|---|
| first (new chat) | 13 after the query | (query at 4,126 page time) | 4,459 after the query | same frame | 4,842 after the query |
| follow-up 1 | 28 | 17 | 1,695 | 1,695 | 1,727 |
| follow-up 2 | 80 | 72 | 2,232 | 2,232 | 2,279 |
| follow-up 3 | 35 | 21 | 1,519 | 1,519 | 1,568 |
| follow-up 4 | 153 | 144 | 1,699 | 1,699 | 1,748 |

Five earlier follow-ups (the first rig version, whose Enter timestamp was
wrong) took 1,667 to 2,234 ms from the echo to the first agent frame, which
agrees. The first agent frame and the first token always arrived in the
same animation frame: for a one-word reply there is no visible
"working" state before the text, and the rig found no streaming indicator
to time separately.

Tokens reach the browser over the session's SSE event feed, not the
WebSocket; the WebSocket carries the `query` frame, `session_created` (117 ms
after the query on the first send) and `resources_changed` notices.

Server side, from the worker log for the throwaway chat (the
`perf.agent_startup` stage lines are not on this revision; these are the
existing `[WS]` and runtime lines):

- First send: `[WS] SDK connect 0.4s (reuse=False)`, then
  `Streaming complete: 11 events in 3.7s`.
- Each follow-up: `SessionRuntime: started ... turn`, `Registering 37
  builtin tool(s)` about 50 ms later (350 ms once), `[WS] Reusing pooled
  client` 2 ms after that, then `Streaming complete: 8 events in 1.4 to
  1.9 s`.

So of the 1.5 to 2.2 s to the first token on a follow-up, the worker spends
about 50 to 180 ms before the model call and the model provider the rest.

### Server side, measured (2026-10-07, lab)

An isolated preview of main (own PostgreSQL, data dir and port; empty
database; no project) with a custom OpenAI-format provider pointing at a
loopback stub that streams "OK" at once. The `perf.agent_startup` stages,
plus the stub's receive time for the model request, per follow-up (ms,
N=6, before the change):

| stretch | ms |
|---|---|
| runtime start to `options_built` | 22 to 25 (`build_options_from_profile` 12.5 to 14.4, of which `create_builtin_tools_server` 4.5 to 5.6) |
| `adapter_ready` (pooled client reused) | 1 to 2 |
| `submitted` | 5 to 6 |
| `first_event` | 5 to 8 |
| `first_event` to the model request | 42 to 44 |
| runtime start to the model request | 78 to 81 |

A new chat on a warm process adds the connect (`adapter_ready` 31 ms, of
which `connect_with_sdk_options` 27 to 29 ms); the first chat after a
process start pays about 540 ms once (imports and caches).

A 1 ms wall-clock stack sampler of the event-loop thread put 13 ms of each
follow-up's `first_event` to request stretch in `httpx` loading the CA
bundle: fluid's Anthropic and chat/completions clients built and closed an
`httpx.AsyncClient` per model call, so every turn (and every tool-loop
step) also opened a fresh TCP and TLS connection. The rest of that stretch
is the event loop waiting on database writes of the turn's events.

What this changed in the candidate list:

- Project 1 (builtin registry per process): the registry costs about 5 ms
  per turn, not 50 to 100 ms; the 50 to 350 ms in the live log is the whole
  options build. Not worth restructuring; not shipped.
- Project 2 (pre-connect a new chat): the connect is about 30 ms in the lab.
  The live 0.4 s was not reproduced, so a reservation in the pool is not
  justified by this measurement; not shipped.
- Shipped instead: one provider HTTP client per native session and one TLS
  context per process (`app/core/provider/harness_adapter.py`, kill switch
  `AI_SHUFFLE_PERF_PROVIDER_HTTP_REUSE`). Follow-up runtime start to model
  request 78 to 66 ms median (N=12 after). Against a remote provider it also
  keeps the TLS connection between model calls that come within httpx's
  5 s keep-alive (tool-loop steps); that gain was not measured.

1. `turn.usage` replay bloat: 80% of every chat's replay; about 4.4 s of the

   sidebar complete 620 ms after the composer, about 0.4 s to gain.
